# Architecture Overview — local presentation

Status: local-only, read-only illustration. No network requests, inference, tools, live decisions or live Events are generated by this page. Existing use-case pages remain unchanged.

## Four categories

The page has exactly four direct-selection buttons: Overview, Access Control, Guardrails, Routing Rules. There are no nested menus or individual-case headings here. These are representative feature stories, not an exhaustive replay of every live case.

## Presenter steps

Each category now finishes in **6 steps With Gateway**, or **4 steps Without Gateway**, including Overview and both Guided/Live Agent. A click starts the ordered animation beats inside that step; it does not require another click for every network leg or processing point. Next/Back/Restart or a category/mode change cancels the previous animation and timers. Hidden tabs stop animation; reduced motion shows the final static beat for that step.

| Category | Six-step With Gateway walkthrough |
| --- | --- |
| Overview | Configure → Browser request → Browser response → Agent request → Agent response → Events |
| Access Control | Configure → Read-only round trip → Restricted request → Deny → Return denial → Events |
| Guardrails | Configure → Inspect/redact request → Inspect/deliver response → Untrusted request → Block/return denial → Events |
| Routing Rules | Configure → Primary request → Primary 503 → Backup route → Answer returned → Events |

Configuration and out-of-band Events stay separate from request/response traffic. Grouping preserves the original leg order, validation, denials and caller-specific return paths.

## Flow audit

- **Overview:** complete Browser → App → Gateway → Model → Gateway → App → Browser round trip, followed by AI Agent → App → Gateway → MCP → Gateway → App → AI Agent. Each response returns on its originating branch. Model and MCP responses are separate transactions, not a multicast answer.
- **Access Control:** read-only MCP operation allowed and returned; restricted MCP operation denied and that denial returned. Guided uses prescribed calls. Live Agent shows Browser job initiation, direct Workers AI inference, tool proposal, trusted app validation/dispatch, then Gateway MCP authorization. The first result returns to Browser before the next presenter-triggered task and its second tool proposal. This is not an autonomous model loop or a claim that tool results are submitted back to the model. The bounded agent controller and app share a Worker; this is not process isolation. Actual models may refuse or propose a different tool; illustration outcomes are not claims about the next live run.
- **Guardrails:** applicable controls evaluated, synthetic sensitive request redacted before inference, model response returned to Gateway and inspected under the assigned response policy before delivery. A separate injected-content request is denied before inference. Without Gateway may still receive model refusal; no automatic disclosure is claimed.
- **Routing Rules:** Gateway evaluates applicable controls, sends to Primary, receives controlled HTTP 503, chooses configured Backup, then returns its answer to Browser. Without Gateway returns the Primary error and never calls Backup. Both adapters currently use the same underlying Workers AI model.

## Policy, data and Events

The configuration step and dashed Vision One → Gateway line describe the **logical management relationship**. Vision One is where administrators configure access rules, routing and guardrail assignments. Gateway evaluates requests against the applicable controls.

Official Controls documentation specifies Access Control → Routing Rules → applicable Guardrails. MCP access checks do not imply that LLM routing applies to every MCP operation. Response inspection is shown only in the Guardrails story representing the demo's assigned response policy, not as guaranteed inspection for every other resource.

Do not depict Events as an authorization lookup, or the Vision One web console as a hop the prompt must traverse. Events are out-of-band observability. Their final presentation step is an explanatory grouping, not a guarantee they are emitted only after response delivery, synchronously, or for every call regardless of logging settings.

Not verified here: configuration push vs polling/cache implementation, any per-request control-plane dependency, telemetry transport/buffering interval, or physical placement of the guardrail detection service. The diagram does not assert these details or that all detection runs inside the EKS pod. It illustrates application/Gateway roles, not a packet capture.

## Deployment boundaries

Browser is the UI caller. App/compute, bounded agent controller, trusted tool dispatch, model adapters and synthetic MCP service run in the Worker. Workers AI performs inference; D1 stores synthetic state/receipts. Gateway with its Redis dependency and private transport connector runs on AWS EKS. The high-level picture omits the private VPC/Tunnel transport, ports and upstream adapters; logical arrows are not direct socket connections or new deployments. Agent has direct Workers AI reasoning in this demo; only its dispatched MCP calls traverse Gateway. Without bypasses Gateway in this controlled demo, not a general recommendation to enable bypass in an enterprise deployment.

The UI deliberately omits the Cloudflare brand word as requested, without changing deployment or runtime behavior. Secrets remain server-side; this presentation neither reveals nor modifies them.

## Validation

The storyboard tests validate connected edge sequences, outbound/return parity, independent Browser and Agent round trips, configuration/data/telemetry separation, MCP denial, inspection ordering, Primary-error-before-Backup, and absence of Gateway traffic on direct paths. Browser checks validate category switches, Guided/Live Agent, With/Without, Back/Next/Restart and rendering. These checks are not live Gateway UAT.
